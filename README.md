# 电商用户增长：从亿级行为洞察到 ChatBI 数据产品

> 个人产品作品 · 数据洞察 → 策略 → 原型 → MVP 全链路
> 技术/分析实现仓库：[user-behavior-analysis](https://github.com/paradisewe/user-behavior-analysis)

**简要描述**

- 基于 100 万用户、1 亿行淘宝真实行为数据，用漏斗与假设检验找出核心增长杠杆：**加购人群购买转化率 5.98%，约为整体 4 倍**（z=30.8，p<0.001）→ 制定"营销资源向加购环节倾斜 + RFM 分层运营"两大策略
- 用墨刀完成 3 组产品原型（ChatBI 查询界面 / 促加购策略 / 增长闭环），定义 8 条全分支验收用例
- 独立落地 MVP：**ChatBI 智能分析助手**——业务方用自然语言直接查询亿级明细，替代"提需求、排期等待"的传统取数流程

## 一、问题与目标用户

**目标用户**：电商运营与业务同事（数据需求方），以及支撑他们的数据团队。

| 痛点 | 现状 | 产品机会 |
|------|------|----------|
| 查数靠排期 | 业务方每次取数需向数据团队提需求、等待排期，简单指标也要以天计 | 自助式 ChatBI：自然语言提问，秒级返回数据与解读 |
| 运营凭经验 | 营销资源平均撒网，高转化环节被忽视，流失原因不明 | 用数据证据重排运营优先级，并用实验机制验证后再上线 |

**产品定位**：一套数据驱动的增长策略 + 一个让业务方自助分析的 ChatBI 数据产品 MVP。

## 二、数据洞察：把"凭感觉"变成"看证据"

每条结论 → 对应一个策略决策（完整口径与检验过程见技术仓库）：

| 洞察 | 数据 | 决策 |
|------|------|------|
| 加购是核心转化杠杆 | 浏览→购买 1.41% vs 加购→购买 5.98%，约 4 倍（z=30.8，p<0.001） | 营销资源向"促加购"倾斜：加购未购人群定向权益、购物车挽回 |
| 浏览大量空转 | 93.4% 的浏览无任何后续行为（路径桑基图） | 在浏览→加购环节投放干预：个性化推荐位、收藏加购激励 |
| 少数客群贡献主体价值 | 重要价值客户占 19.4%、人均购买 5.1 次（RFM） | 分层差异化运营：高价值保体验、潜力客群促频次、流失预警客群做召回 |
| 业务波动缺乏解释 | 12-02 DAU 环比 +31.1%，次日留存跳升至 98.3% | 建立 DAU/漏斗/留存/复购指标体系，异常可归因（老用户回流+新用户涌入） |

## 三、需求定义与优先级：做什么，更决定不做什么

- **按投入产出比排序需求**：将候选深化方向整理为优先级清单，先做统计检验与指标体系（低成本高置信），再做 A/B 框架与 AI 助手。
- **快速止损**：类目协同过滤推荐原型经时间切分评估，效果仅为热门基线的 0.48 倍——判定 9 天窗口内共现信号不足，停止投入而非继续堆功能（结论如实保留在仓库）。
- **上线前必须过实验**：策略不直接投放。A/B 框架内置功效分析（当前总体 MDE=2.27pp）、SRM 校验与 AA 校准（200 次 AA 假阳性率 4.5%，与理论 α=5% 一致），把"先验证再全量"固化为流程。

## 四、产品设计

**原型**（墨刀，3 张展板、9 个帧，桌面 1440×900 ×4 + 移动 375×812 ×5）：

1. ChatBI 查询界面：提问 → 结果表格/图表 → AI 解读的三段式信息架构
2. 促加购策略页：目标人群、触点、权益与预期指标
3. 增长闭环总览：洞察 → 策略 → 实验 → 复盘的业务旅程

**核心用户旅程（ChatBI）**：业务方输入自然语言 → 意图路由 → SQL 查询 / 知识问答 / 多步自动分析 → 返回数据 + 图表 + 结论解读。

**验收标准先行**：发布前定义 8 条覆盖全部路由分支的验收用例（如"昨天 DAU 多少"须返回精确值 970,401），逐条验证通过后才上线。

## 五、MVP：ChatBI 智能分析助手

- **产品架构**：Dify Chatflow 四分支——知识 RAG / 固定 NL2SQL / Agent 自动分析 / 兜底，各支路独立应答节点；模型按任务复杂度分级调用（分类轻量、SQL 生成旗舰）。
- **数据底座**：自研 SQL 工具服务以 OpenAPI 暴露 query_sql / get_schema / health_check 三接口，DuckDB 直连 1 亿行明细，SQL 全量结果与抽样分析交叉验证一致。
- **工程取舍记录**（细节见技术仓库 Expands.md）：分类器小模型不稳定→换云端模型；模型输出格式漂移→服务端宽容解析；容器网络隔离→SSRF 白名单放行。
- **边界与现状**：在线看板公网可访问；AI 助手 MVP 依赖本机服务常驻，当前为可现场演示状态，生产化还需服务云端部署与鉴权。

## 六、复盘

**做得好的**：洞察到决策链条完整、数字全部可复现（SQL/Python 双口径交叉验证）、主动暴露负结果。

**诚实的不足**：痛点来自业务协作观察与数据反推，未做正式用户访谈；策略停留在方案与模拟实验，无线上投放效果归因；AI 助手未做多用户真实使用测试。

**下一步**：助手服务上云 + 使用埋点，用真实提问日志迭代意图路由准确率。
